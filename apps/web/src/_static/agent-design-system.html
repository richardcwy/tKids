01

The field.

Six products defining how agent interfaces work today. Each makes different choices about where the chat ends and the work begins, how tools are surfaced, how trust is earned, and how output is presented. Worth borrowing from selectively — none of them are built for our context, but they've solved problems we'll face.

01.A
Reference implementation

Claude

MakerAnthropic
SurfaceWeb, desktop, mobile
DefiningArtifacts, Projects, MCP

Claude's most distinctive contribution is the Artifacts panel — a persistent canvas to the right of the conversation that holds substantive output (documents, code, interactive widgets) so the chat itself stays a transcript rather than a scrolling pile of generated content. Tool calls render inline as collapsible cards that expand to show inputs and outputs. The composer surfaces a tools menu rather than mode-switching the whole product. Projects bundle a chat history with shared instructions and uploaded knowledge — the closest thing to "workspaces" in a single-user product. MCP exposes a consistent shape for connectors: any external tool advertises a set of capabilities Claude can invoke, with the user reviewing what gets used.

BorrowThe artifact panel pattern. Substantive output gets its own surface.
BorrowCollapsible tool-call cards as the default trust mechanism.
AdaptProjects → Workspaces. We need shared, multi-user, role-aware versions.
01.B
Volume leader

ChatGPT

MakerOpenAI
SurfaceWeb, desktop, mobile
DefiningCanvas, GPTs, Memory

ChatGPT introduced Canvas — the same idea as Artifacts under a different name — and leans heavily on suggestion chips as a follow-up affordance. Custom GPTs package an instruction set, knowledge files, and tool permissions into a named, shareable agent — a useful primitive even if the directory has been a mixed success. The tools menu is more prominent than in Claude (image gen, code interpreter, browse, deep research are toggles the user actively chooses). Cross-conversation memory is exposed as an editable panel — users can see and delete what's been remembered.

BorrowSuggestion chips as a navigation aid, not just decoration.
BorrowMemory as an inspectable, user-editable list. Trust requires legibility.
CautionTool toggles in the composer can pile up. We'll need more careful disclosure.
01.C
Embedded paradigm

Cursor

MakerAnysphere
SurfaceIDE (forked VS Code)
DefiningInline diffs, Composer mode

Cursor is the strongest argument that standalone chat is not the only shape an agent can take. The agent lives inside the IDE; its primary output is not text in a thread but inline diffs rendered in the file the user is already reading. The chat is a sidebar, less for conversation than for issuing commands and reviewing what changed. Composer mode runs multi-file edits with a review-and-accept gate per change. Worth studying because the underlying design question — how an agent presents structured output for review — is exactly ours, even if our delivery surface is different.

BorrowInline review-and-accept patterns. Diff surfaces apply beyond code.
BorrowPer-change granularity. Accept some, reject some, regenerate one.
QuestionIs our agent a destination or an embed? Probably both, with a shared design language.
01.D
Citation-first

Perplexity

MakerPerplexity AI
SurfaceWeb, mobile
DefiningInline citations, Spaces

Perplexity treats citations as a first-class UI element, not an afterthought. Every claim carries a source chip; every source has a card with title, favicon, and excerpt. The product reads like a research tool with a chat affordance rather than a chat product with search bolted on. Spaces group threads by project and let users add their own files to scope the answer. Pro Search exposes the reasoning steps as expandable rows — a more readable take on chain-of-thought than the "thinking" panels in other products.

BorrowInline citation chips as a non-negotiable. Every grounded claim links back.
BorrowSource cards with favicon + title + excerpt. Aim for this density.
BorrowReasoning shown as expandable steps, not a wall of italic text.
01.E
Enterprise embed

M365 Copilot

MakerMicrosoft
SurfaceEmbedded in Office apps
DefiningGraph context, DLP awareness

Copilot is the most directly relevant reference for an enterprise platform. The agent is embedded into the apps users already work in (Word, Excel, Outlook, Teams), with a standalone chat as a secondary surface. It reads context from the Microsoft Graph — emails, documents, meetings — and that context is visible, not hidden. Compliance is part of the product: the UI shows when something can't be cited because of permissions, when a response is bound by data-loss-prevention rules, and which sources are internal vs. external. The aesthetic is conservative on purpose; this is the right register for a tool that touches sensitive data.

BorrowPermission-awareness shown explicitly. "You don't have access to X" is its own state.
BorrowInternal vs. external sources distinguished visually.
BorrowConservative register. Users with audit obligations don't want a quirky agent.
01.F
Workplace search

Glean

MakerGlean
SurfaceWeb, mobile, embeds
DefiningConnector-first, ACL-aware

Glean was a search product that grew into an agent platform — its UI bears the marks of that lineage. The connector ecosystem is the product: a settings page that looks like a logo wall of every SaaS the company uses, with status, last-sync, and permission scope per connector. Every result respects ACLs — users see only what they're authorized to see, and the UI surfaces this rather than hiding it. Agents in Glean are named workflows users can invoke (e.g. "summarize last week's customer calls") with explicit scope and source list.

BorrowConnector grid as a primary admin surface. List, status, scope.
BorrowACL-aware results. The agent shows what each user is allowed to see.
BorrowNamed agents as reusable, scoped workflows — not just freeform chats.
02

Principles.

Six commitments the design system encodes. These are the answers we've already made — when a component decision feels ambiguous, return here.

i.

The conversation is the spine.

Chat is not a feature, it's the substrate. Every other surface — artifacts, connectors, audit logs, settings — is a side door off the conversation. The interface should feel like the user is in one continuous dialogue, not navigating a multi-page application that occasionally shows them an LLM response. Cards, panels, and modals all serve the chat; they never replace it.

ii.

Show the work, always.

Tool calls render as cards. Citations resolve to source previews. Reasoning is exposable on demand. When the agent reaches into a connector, the user sees which one, with what query, and what came back. Hidden work is the fastest way to lose enterprise trust — not because users will read every trace, but because they need to know they could.

iii.

Permission boundaries are visible.

The agent operates inside an ACL graph. When a user lacks access to something, the UI says so explicitly rather than producing a thinner answer. "Three sources excluded — you don't have access" is more trustworthy than a quietly-degraded response. This applies to source citations, connector calls, and shared workspaces alike.

iv.

Substantive output gets a canvas.

If the user is going to copy it, edit it, share it, or come back to it, it doesn't belong inline in the message stream where it'll scroll away. Documents, code, decks, dashboards, structured plans all open in the artifact panel — persistent, addressable, version-tracked. The chat keeps the dialogue clean; the canvas keeps the work.

v.

Iteration is a first-class action.

No agent gets it right the first time, every time. Regenerate, edit, branch, undo, and accept-this-but-not-that should be available wherever they make sense — at the message level, the artifact level, the per-edit level. The user should never feel locked into a response or have to start over to refine.

vi.

Everything the agent does is recoverable.

In an enterprise context, the agent acts on behalf of someone — that someone is accountable. Every tool call, every connector touch, every artifact edit is logged to an audit trail the user (and admins, where appropriate) can inspect. Destructive actions require explicit confirmation. The system should make it impossible for an agent action to disappear silently.

05

Scenarios.

Four ways the agent gets used in practice — the shapes a turn can take. The dialogue is the bedrock; the others are what the agent reaches for when a plain answer isn't the right response. Each scenario is built from the components in §04, and together they define what the framework in §06 has to support.

i.
When the answer is the work

The dialogue

A user asks something. The agent grounds the answer in workspace data and replies in prose with citations. The user follows up; the thread accrues context. No artifact, no form, no destructive action — just a conversation about what the workspace knows.

Step 1User asks
What's our parental leave policy for new hires? My team is hiring someone whose partner is due in March.
Step 2Agent grounds the answer
Searching HR Knowledge Base
Knowledge Base 3 documents matched 0.8s
query: parental leave policy new hire eligibility
scope: HR Policies (workspace-scoped)
filters: current year, employee handbook
Step 3Agent responds with citations
Eligible employees get 16 weeks paid leave regardless of role or tenure1. New hires qualify from day one — there's no waiting period1. Leave can be taken any time within the first year after the birth or adoption, and can be split into up to two blocks2.
1
Employee Handbook 2026 · §4.2 Parental Leave
notion.so/acme/handbook · last updated Feb 12 · internal
"All employees, regardless of tenure, are eligible for 16 weeks of fully paid parental leave starting from their first day of employment."
Step 4User follows up
Does adoption count?
Step 5Agent extends
Yes — the policy treats adoption and surrogacy the same as biological birth, including same-sex partners and non-primary caregivers3. The 16-week clock starts at placement rather than birth.
Why it matters. The dialogue is the default — the agent should reach for it first, not for forms or artifacts. Every claim is grounded in a source the user could open. Suggestion chips invite a follow-up without forcing the user to type one.
ii.
When the request is ambiguous

Clarifying the ask

Some requests are too underspecified to answer well. Rather than guess and produce something the user has to reject, the agent asks structured questions back. Not a free-form "could you tell me more?" — a bounded card with the actual choices that disambiguate the request.

iii.
When structured data is required

Collecting structured input

Some tasks require fields a chat conversation handles poorly — dates, currencies, file attachments, controlled vocabularies. The agent presents an inline form, the user fills it, the agent submits to a downstream system. Forms appear in the conversation stream, not in a separate page.

iv.
When the output is the work

The artifact loop

For substantive output the user will edit, share, or send — documents, emails, code, decks, plans. The artifact opens in the canvas. The user reviews, requests revisions in the chat, and the agent updates the artifact in place. Versions are persistent. Sending or committing requires explicit approval.

06

Framework architecture.

The scenarios in §05 share a structure. A turn is a sequence of typed blocks; a thread is a sequence of turns; a workspace defines what the thread can reach. Everything else — connectors, artifacts, audit, policy — hangs off these primitives. This section names them.

06.A

Layers

Five layers, bottom to top. Each one assumes the layers below it and is rendered by the layers above it. A clean break between them means UI changes don't touch orchestration logic, and connector changes don't touch UI.

Layer 5 Surface
The rendered UI — components from §04, composed into the patterns from §05. Pure presentation; no business logic.
message tool-card artifact-panel composer dialog
Layer 4 Composition
The block / turn / thread model. A turn is an ordered list of typed blocks. A thread is an ordered list of turns. Branching, undo, and version history live here.
Block Turn Thread Artifact Workspace
Layer 3 Orchestration
The agent loop: planning, tool routing, intermediate state, retries, human-in-the-loop checkpoints. Decides which blocks to emit next given the thread state and the user's last input.
planner router checkpoint retry-policy
Layer 2 Capability
Connectors and tools the agent can call. Each one declares its actions, inputs, outputs, and required permissions. MCP-shaped where possible — a capability is a contract, not a hard-coded integration.
Connector Action Schema Scope
Layer 1 Trust
The substrate everything else respects: identity, ACLs, policy enforcement, audit. Every action and read passes through here. Without this layer, none of the others can be exposed to enterprise users.
Identity ACL Policy Audit DLP

06.C

Anatomy of a turn

A turn is the unit of agent activity in response to a user input. It owns blocks, references artifacts, and emits audit entries. Concretely:

Turn schema · simplified
type Turn = {
  id: TurnId
  thread_id: ThreadId
  parent_turn_id: TurnId | null  // supports branching
  input: { role: 'user', blocks: Block[] }
  output: { role: 'agent', blocks: Block[], status: TurnStatus }
  artifacts_touched: ArtifactRef[]  // created or updated
  actions_taken: ActionRef[]  // all logged to audit
  sources_cited: SourceRef[]
  policy_decisions: PolicyDecision[]  // permits, denies, redactions
  timing: { started_at, finished_at, tokens, cost }
}
06.D

The lifecycle of a request

When a user sends a message, this is the path it walks. The diagram is read top-to-bottom; each step is gated by the trust layer.

1 · Receive
Validate input. Check identity, workspace, and policy. Reject before reaching the agent if the user can't be in this thread, or if the workspace is locked. Emit an audit entry either way.
2 · Plan
Decide the shape of the response. Dialogue, clarification, form, or artifact loop? Which connectors will this need? The planner output is itself a turn-shape: the ordered list of block types the agent intends to emit.
3 · Authorize
Resolve missing access before execution. If the plan calls for a connector the user hasn't authorized, emit a connector_ref block and pause. The thread resumes once the user grants scope.
4 · Execute
Run the plan, streaming blocks as they're produced. Tool calls happen here, gated by the trust layer per call. Artifacts are created or updated. Side-effecting actions stop and emit a confirmation block instead of executing.
5 · Cite
Attach sources to claims. Citations resolve against the documents the agent actually read in step 4. Claims without a source either get phrased as inference or removed.
6 · Settle
Close the turn. Write to audit: actions taken, artifacts touched, sources cited, policy decisions. Suggest follow-ups. The thread is ready for the next input.
06.E

The workspace as the unit of policy

A workspace is more than a folder of threads. It's the scope inside which the agent operates: which connectors are bound, which members can see which threads, which DLP rules are in force, what the audit retention is.

Threads belong to a workspace. Switching workspaces is not switching context — it's switching what the agent is allowed to see and do. This is the boundary at which most enterprise deployment decisions get made.

A workspace declares
membersIdentities + roles allowed in
connectorsBound sources with per-scope permissions
policiesDLP rules, external-source allowance, model selection
auditRetention period, who can read the log
defaultsSystem prompt, tone, named agents available
06.F

How scenarios compose from blocks

Each scenario from §05 is a recurring shape — an ordered sequence of block types — that the framework knows how to render and orchestrate. New scenarios don't require new code; they require new sequences.

i. The dialogue
textuser → status → tool_call → textagent + citation* → picker
ii. Clarifying the ask
textuser → textagent → clarify → textuserselections → textagent → status → ...
iii. Collecting structured input
textuser → textagent → form → textusersubmission → tool_call → textagent
iv. The artifact loop
textuser → textagent + artifact_ref → textuseredits → diff + artifact_refv2 → textuser → confirmation → tool_call
v. Connecting a source
textuser → textagent → connector_ref → [scope dialog] → status → ...resume original plan
