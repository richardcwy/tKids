## 2. Donation crowdfund (the big one)

### Product change — "Ignite by goal, not by date"

**Current narrative** (v1.0):
> "EP drops June 1, 2026. Join the fanclub to be first to hear."
> Countdown: `43:11:43:44`

**New narrative** (v1.1):
> "We're crowdfunding the EP. When we hit the goal, Ignite! ships. Your support makes the first press real."
> Progress tracker: `NT$127,500 of NT$300,000 · 83 backers · 42% to drop day`

This is a product pivot, not a feature. It changes:
- Hero copy (countdown → funding tracker)
- Marquee text (`out 06.01.26` → `funding open · ignite when we hit goal`)
- Fanclub CTA (still "join the fanclub" but optionally add "fuel the first press")
- Welcome email (tweak the single line about "drops June 1")
- Open Graph descriptions + JSON-LD `datePublished` field (set to TBD / remove)
- Privacy policy vendor list (add Polar + Stripe as processors if we wire payments)
- Error messaging for the donation flow

### ⚠ Product decisions that gate implementation

I need your answers on these before I write any code. Recommending defaults:

**D1. Goal amount?**
Options: NT$150k (modest, achievable), NT$300k (ambitious, typical first-press EP in TW), NT$500k+ (stretch).
→ Recommend: **NT$300k**. Easy to explain ("the real cost of a 5-track EP: mastering, physical press, artwork, distribution"), high enough to feel meaningful, low enough to be hit by ~300 supporters at ~NT$1,000 each.

**D2. Timeline behavior if goal hits / misses?**
Options:
- **A) Hit-or-miss with hard deadline** (2026-07-31). If hit → EP drops in Aug. If missed → refund all donors.
- **B) Soft campaign, no refund** (funds go to production regardless). EP drops whenever we hit the goal, even if it takes 6 months.
- **C) Tiered goals** — NT$150k = digital release, NT$300k = physical press, NT$500k = vinyl + music video.
→ Recommend: **B with optional C on top**. Soft campaign is simplest legally (no MoR refund logic), and it matches the "T-community lifting up three kids" thesis — patrons aren't buying the EP, they're funding its existence. Tiered stretch goals add excitement at milestones.

**D3. Donation tiers?** (what do backers get for different amounts)
Options:
- **Minimal**: single `NT$ any amount` button, no tiers.
- **Three tiers**: NT$200 (thank-you email + name on "supporters" page), NT$1,000 (physical CD + signed photo card when pressed), NT$3,000 (private video message from the kids).
- **Five tiers**: Above + NT$5,000 (handwritten letter), NT$10,000 (Zoom meet-and-greet).
→ Recommend: **Three tiers** as the default. Add two more if founder wants. Tiers dramatically increase conversion vs. "any amount" — people anchor on the middle tier.

**D4. Payments platform?** (flagged in eng review as blocker for TW entity)
Options:
- **A) Polar** — integrated with Better-Auth (scaffold already there), MoR handles VAT/tax, but **TW entity acceptance unverified**. Outside-voice flagged this as a real risk.
- **B) Ko-fi** — no MoR onboarding, instant setup, 0% platform fee on one-time + 5% on monthly. Less integrated (iframe embed + email-based receipts). No access to supporter list from our DB.
- **C) Stripe Payment Links + manual reconciliation** — Stripe onboards TW entities reliably. We lose in-site auth-linked donations but get full control. Can wire webhooks → Turso `donations` table ourselves.
- **D) Use BOTH** — Polar primary, Ko-fi banner as an escape hatch "Taiwan bank? Use Ko-fi instead."
→ Recommend: **A (Polar) as primary, B (Ko-fi) as tested fallback.** I'll write both into the plan. Day-1 implementation tries Polar onboarding; if TW rejects, swap to Ko-fi with a 2-hour code change (we replace the Polar checkout button with a Ko-fi widget — the rest of the funding tracker UI is unchanged).

**D5. What does the funding tracker show?**
Required: goal + raised + % + backer count.
Optional: recent supporters list, recent donation amount/message ticker, countdown to campaign end (if we pick D2-A).
→ Recommend: **required fields only for v1.1.0420**. Recent-supporter ticker and donation messages go in v1.2 if they feel needed.

**D6. Does existing fanclub signup get asked to donate?**
Options:
- **A) Silent** — the fanclub signup page stays as-is; only the hero mentions donation.
- **B) Post-signup**: after signup success, a "Now fuel the first press" banner.
- **C) Both** — dashboard page for logged-in users shows their donation status + donate button.
→ Recommend: **B for v1.1.0420**. C can come later. The existing fanclub base (50-500 T-community members) is the most likely donation conversion pool; don't waste that conversion moment.

### Current state (v1.0)
- `<html lang="zh-TW">` single-locale
- Inline bilingual copy (EN + zh-TW) within the same HTML
- Noto Sans TC font installed
- No routing, no switcher, no translations-as-data

### Target state (v1.1)

- Language switcher in nav
- Per-locale OG tags + hreflang alternates
- Per-locale welcome email (`apps/web/src/lib/emails/{locale}/welcome.html` or one file with locale branching)

### Implementation plan

**Astro i18n configuration** — Astro has built-in locale routing since v3. Update `astro.config.mjs`:
```ts
i18n: {
  defaultLocale: "zh-TW",
  locales: ["zh-TW", "en", "ja", "de"],
  routing: {
    prefixDefaultLocale: false,  // zh-TW at /, others prefixed
    redirectToDefaultLocale: false,
  },
  fallback: { en: "zh-TW", ja: "zh-TW", de: "zh-TW" },
}
```

**Content as data, not as template**:
Move all user-visible copy out of Astro components into `apps/web/src/i18n/{locale}.json` files. Shape:
```
{
  "hero": {
    "slogan": "Ignite and shine!",
    "manifesto": "..."
  },
  "lineup": {
    "sectionTitle": "three kids",
    "sectionMini": "點亮宇宙的三個男孩",
    "ctaListen": "listen to \"Ignite!\""
  },
  "join": { ... },
  "footer": { ... },
  "privacy": {...},
  "signup": {...}
}
```

Components consume via a `t()` helper:
```ts
import { useI18n } from "@/i18n";
const { t, locale } = useI18n(Astro);
// t("hero.slogan")
```

No framework dependency — 50-line helper using JSON.parse(globImport).

**Fonts per locale**:
- `zh-TW` → existing Noto Sans TC
- `en`, `de` → Unbounded + DM Serif + Instrument Serif + JetBrains Mono (already installed; Latin + Cyrillic covers both)
- `ja` → add `@fontsource/noto-sans-jp` (chinese-japanese subset, ~40KB per weight)

**Component changes**:
- `Nav.astro` adds a small language switcher (`EN / 中 / 日 / DE`) on the right; state stored in a cookie, also in the URL path
- `Layout.astro` sets `<html lang={currentLocale}>` dynamically
- `Hero.astro`, `Lineup.astro`, `MemberCard.astro`, `Marquee.astro`, `Footer.astro`, `SignUpForm.astro`, `SignInForm.astro`, `privacy.astro`, `dashboard.astro` — all swap hardcoded strings for `t(...)` lookups
- `SEO.astro` emits `<link rel="alternate" hreflang="{each locale}" href="...">` tags and swaps OG / JSON-LD per locale
- `resend.ts` — welcome email accepts a `locale` param and picks the right template string

**Translation sources**:
- **zh-TW**: already in code; extract to `zh-TW.json`
- **en**: currently inline in the bilingual copy; extract to `en.json`
- **ja**: **needs translation**. Recommend: Claude for first draft + native-speaker review before shipping. Do NOT use auto-translation for the privacy policy.
- **de**: **needs translation**. Same deal.

Privacy policy in 4 languages is where human review is non-negotiable. Budget: 1-2 hours of a native speaker per language, or $200-400 with a translation service.

### Routing nuance
- Canonical URL on the site is `https://tkids.tw/` (zh-TW content)
- Language switcher adds `/en`, `/ja`, `/de` paths
- `Accept-Language` auto-detection on first visit: redirect to preferred locale once, store preference in cookie so back button works intuitively. Opt-out: `?nolang=1` query param stays on explicit URL.

### Risks
- **Font weight**: adding Noto Sans JP adds ~60KB to the JS bundle for ja visitors. Each locale prefetches only its own font via `<link rel="preload">`.
- **Translation drift**: if we update the hero slogan in zh-TW, the other 3 files need to stay in sync. We could add a CI lint that checks key parity between locale JSON files.
- **hreflang mistakes**: wrong hreflang tags get Google confused about which variant to rank. I'll add a test case that parses the final HTML and asserts hreflang correctness.
